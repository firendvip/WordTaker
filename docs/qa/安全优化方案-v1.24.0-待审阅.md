# 弦外小猫 安全优化方案（待审阅 · 暂不开发）

> 依据《安全审计报告-v1.24.0-安装包》。本文只出方案供决策，经审阅确认后再派单开发。
> 日期：2026-07-09

## 0. 总原则（先对齐认知）

- **权威判定必须在服务端。** 客户端是不可信环境，凡"能不能用/扣多少费/送不送额度"都不能信客户端上报。报告已证实扣费链路是安全的，要守住。
- **客户端侧只能"提高破解成本"，不能"绝对防护"。** 尤其本地提示词——本地推理必须把 prompt 喂给本地模型进程，理论上有决心的逆向者总能从内存拿到。目标是把"解包即得"（零成本）提高到"需要动态逆向+内存分析"（高成本、且可远端吊销），并让泄露后损失可控。下文对每档方案都会诚实标注"挡得住谁、挡不住谁"。

---

## 1. 本地模型提示词保护（重点专章）

### 1.1 现状与威胁
- 现状：`llm_server.py:75-104` 完整明文，`asar extract` 零门槛可读，可 1:1 复刻、可据分隔符精确构造越狱注入。
- 威胁分级（要防到哪一层，决定选哪档）：
  - T1 **好奇用户 / 竞品**：解包 grep 看一眼就抄走 —— 当前完全挡不住。**这是主要要堵的**。
  - T2 **脚本小子**：会跑通用反混淆脚本、看内存字符串。
  - T3 **有决心的逆向者**：会挂调试器、hook 本地模型进程、dump 内存。**本地推理架构下无法根除，只能抬高成本+可远端吊销止损。**

### 1.2 分档方案

| 档 | 做法 | 挡住 | 挡不住 | 断网可用 | 成本 |
|---|---|---|---|---|---|
| **A 轻度混淆** | 提示词不再明文，改为加密串（AES/XOR+盐）存文件，运行时在原生层解密拼接后送模型；分隔符/规则不留明文常量 | T1 grep、一眼看 | T2/T3 断点内存 | ✅ 完全 | 低（0.5–1 人日） |
| **B 服务端下发+内存态**（推荐主线） | App 首次润色时向后端拉取提示词（HTTPS+设备/登录鉴权），仅内存持有、**不落盘明文**；断网时用「加密缓存」降级（见 C） | T1、T2 静态、且**可远端轮换/吊销/按用户下发不同版本** | T3 抓包（HTTPS 内）/内存 dump | ⚠️ 依赖缓存 | 中（2–3 人日，含后端接口） |
| **C 加密本地缓存** | B 的降级：拉到的提示词用「设备密钥(safeStorage/keychain)」加密落盘，断网时解密用；密钥在 OS keychain，不随包分发 | T1、T2 | T3 有 keychain 访问权时可解 | ✅ | 中（并入 B，+0.5 人日） |
| **D 原生模块承载** | 解密逻辑与提示词组装编译进 `.node`(N-API/Rust) 而非 JS/py，字符串不在脚本层 | T1、T2、抬高 T3 门槛 | T3 反汇编+内存 | ✅ | 中高（2 人日，需接现有构建/CI） |
| **E 拆分削价值**（可叠加） | 本地只保留"精简够用"提示词，最完整的规则+few-shot 只在服务端云端润色用；即便本地版泄露，拿到的也不是全部 know-how | 降低泄露损失 | 不阻止泄露本身 | ✅ | 低（0.5 人日，纯内容拆分，需评估本地质量回退） |

### 1.3 推荐组合
**B（服务端下发+内存态） + C（加密缓存降级） + A（本地留存一律加密、无明文常量）**，可选叠加 **E**。

理由：
- B 是唯一能"远端轮换/吊销"的方案——一旦发现泄露，改后端立即让旧版失效，这是明文/纯本地混淆都做不到的止损能力，也顺带能按用户/版本下发差异化提示词。
- C 保证断网仍可用本地润色（不牺牲核心体验）。
- A 兜底：任何落到磁盘的提示词都是密文，彻底消灭"解包 grep 即得"（把 T1 从零成本抬到需动态逆向）。
- D 是可选加固，投入产出一般，**建议二期再评估**，一期先上 B+C+A。
- E 视本地润色质量能否接受精简版而定，**需先做一次质量对比**再决定，不阻塞主线。

**诚实结论**：B+C+A+D 全上，也只能做到"对抗 T3 需要动态逆向+内存 dump 且泄露后可远端吊销"，无法做到数学意义上的不可提取——这是本地推理的固有边界。若要绝对保护提示词，唯一路径是**润色全部走云端、本地模型不再承担该能力**（但那会牺牲"离线可用/不计费"的产品卖点，属产品决策，不在本方案默认范围）。

## 2. 其余安全项方案（对应报告）

### 2.1 P0 — 匿名赠送额度可被脚本无限刷（后端，客户端堵不住）
- 方案（服务端）：① `/quota`+`/polish` 统一限流（IP/设备维度）；② 同 IP/ASN 短时大量"新设备注册"触发风控（拒绝或降赠送）；③ 长期：赠送领取绑定一次低成本强身份动作（短信/图形验证码）而非纯设备指纹；④ 设备指纹作参考信号不作唯一判据。
- 状态：已并入计费后端 P0 核实单，待其回执现状与处理。

### 2.2 P0 — `/payment/mock/pay` 生产可达性
- 方案：核实生产 `look3.cn` 是否已禁用/环境隔离；若可达立即禁用或加管理员级鉴权+环境开关。
- 状态：已并入计费后端 P0 核实单。

### 2.3 P1 — relay token 硬编码（`relayConfig.js:20,22`）
- 方案（二选一）：① 保留 relay 但加来源校验（`x-device-id`+频控限流）+改为版本化短时轮换 token；② 既然主路径已走计费后端，评估**下线该兜底 relay**。
- 归属：杂项功能。建议先确认 relay 是否仍在用，再决定加固或下线。

### 2.4 P2 — Win 端 `CLIENT_PLATFORM = "mac"`（`backendConfig.js:38`）
- 方案：改为 `"win"`；排查是构建注入问题还是源码写死，确保后续打包不复现。
- 归属：Windows 专项。低风险小修，可随下次 Win 发版带上。

## 3. 建议实施顺序与归属

| 阶段 | 项 | 归属 | 粗估 |
|---|---|---|---|
| 一期（安全止血） | P0 额度限流+风控、P0 mock 支付核实 | 计费后端 | 已派核实 |
| 一期 | 本地提示词 B+C+A（下发+加密缓存+消灭明文） | 语音引擎（改 llm_server）+ 计费后端（下发接口） | 3–4 人日 |
| 二期（加固） | 本地提示词 D（原生模块）、E（拆分削价值） | 语音引擎 | 视一期效果评估 |
| 随手 | relay 加固/下线、Win CLIENT_PLATFORM | 杂项功能 / Windows 专项 | 各 0.5 人日 |

## 4. 需你拍板的决策点

1. **本地提示词档位**：确认走推荐的 **B+C+A**（下发+加密缓存+无明文），还是先只做最省的 **A（轻度混淆）**顶一下？（B 能远端吊销，强烈建议；A 仅挡好奇用户）
2. **是否接受残余风险**：认可"本地推理无法绝对防提示词提取、只能抬高成本+可吊销"这一边界？若要绝对保护，需讨论"润色是否全部转云端"的产品取舍。
3. **relay 兜底路径**：还在用吗？决定加固还是下线。
4. **E（拆分削价值）**：是否愿意为降低泄露损失，接受本地润色用"精简版提示词"（可能质量略降，先做对比再定）？

> 以上确认后，我按阶段拆单派发（语音引擎/计费后端/杂项/Windows），每单含验收标准。
